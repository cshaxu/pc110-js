# M2 T2 S6: PCjs-Assisted CPU Integration Gate

## Objective

After S3 CPU, S4 memory, and S5 I/O/reset/stepping completion, prove that the
project-native rebuilt CPU can be the sole executing CPU for the M1 browser
workload before native-device migration starts. The gate temporarily uses
read-only sibling PCjs devices through project-owned adapters.

## Boundaries

- The harness is verification-only and is not a product runtime or distribution
  dependency.
- The PCjs CPU, the legacy CPU, and NXVM must not execute guest instructions in
  the harness.
- The rebuilt CPU retains project-owned state, decode, execution, memory, port,
  reset, and trace contracts.
- PCjs devices remain read-only sibling references. Do not copy or modify their
  runtime source.
- Do not begin native M2 T3 device implementation until S3, S4, S5, and this
  final S6 gate pass.

## Parts

1. Record the exact PCjs device proxy inventory and define project-owned bridge
   contracts for memory, ports, interrupt delivery, DMA requests, reset, and
   emulation time.
2. Build a browser-capable test harness that disables the PCjs CPU and installs
   the rebuilt CPU as the only guest instruction executor.
3. Attach the required temporary PCjs device proxies and boot the M1 DOS
   workload to its documented browser marker.
4. Add focused bridge tests, a compact proxy inventory, and differential trace
   evidence. Verify that no legacy CPU, NXVM, or PCjs CPU runtime path is used.

## Acceptance

- The M1 browser workload reaches its documented DOS marker through the rebuilt
  CPU and temporary PCjs device proxies.
- The harness remains outside the standalone product runtime and uses only
  relative read-only sibling references.
- Every proxy has a declared device kind, interface boundary, replacement owner,
  and native-device verification workload.
- The full project gate, browser check, tracking, provenance, and verification
  record pass before M2 T3 begins.
