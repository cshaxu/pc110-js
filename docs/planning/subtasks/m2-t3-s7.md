# M2 T3 S7: BIOS POST Checkpoints Through Real Device Paths

## Objective

Advance the pinned selected DeskPro 386 ROM through verifiable POST checkpoints
using only project-native device behavior. Every new ROM-visible port or event
must have a named hardware owner, focused tests, trace evidence, and an
explicit boundary; no diagnostic-port discard, firmware service, or synthetic
completion response is permitted.

## Scope And Sources

- Behavioral authority: pinned read-only PCjs
  `machines/pcx86/modules/v2/chipset.js`, selected DeskPro ROM configuration,
  and machine-level port ownership.
- Product code: original TypeScript in `src/devices/`, `src/machine/`,
  `src/reference/`, and existing native CPU/memory/device contracts.
- Initial blocker: selected ROM `OUT 0x84, AL` at `F000:F907` after two
  instructions. PCjs identifies `0x84` as a readable/writable spare 74LS612
  DMA page-register cell used by DeskPro 386 POST checkpoints.

## Boundaries

- S7 may extend existing native device models only when a selected-ROM trace
  reaches a source-established hardware boundary.
- Each ROM advance must preserve ordinary device semantics; POST checkpoint
  storage is not a trace-only sink and must remain readable after a write.
- The selected-ROM trace is evidence, not a replacement for focused component
  and integration tests.
- No PCjs runtime/device import, firmware patch, BIOS service, ignored port,
  host time, guest service, storage, display, DOS, PC110, or browser-input
  behavior is authorized by this subtask.

## Execution Order

1. Record the selected-ROM start, each reached checkpoint, first unavailable
   owner, PCjs evidence, intended native module, and result in a compact POST
   checkpoint ledger.
2. Implement the initial selected spare DMA page-register group, beginning
   with `0x84`, as project-native state with focused read/write/reset tests.
3. Re-run the bounded selected-ROM trace and classify the next real device or
   CPU/memory blocker without adding a synthetic response.
4. Repeat one classified device path at a time until the ROM reaches a named
   POST checkpoint beyond the initial page-register setup.
5. Add truthful browser-visible POST trace/status only after a stable native
   checkpoint exists; it must not claim boot, display, storage, or DOS.

## Verification

- Focused tests cover every mapped spare port's byte-width behavior, retained
  read/write value, reset state, and coexistence with DMA page registers.
- Integration tests prove `OUT 0x84, AL` proceeds through native port dispatch
  and preserves the written checkpoint for a following `IN`.
- `pnpm run trace:rebuilt-rom` records executed instruction count, address,
  reached checkpoints, and first unimplemented hardware boundary.
- Full gate: `pnpm run format`, `pnpm run build`, `pnpm run lint`,
  `pnpm run test`, and `git diff --check`.

## Stop Conditions

- Stop for owner direction only when the next selected-ROM boundary requires
  an unestablished DeskPro-specific chipset behavior, protected asset, or
  source conflict that cannot be resolved through the pinned reference and
  focused component evidence.

## P2 Spare DMA Page Registers

P2 will add the selected `0x80`, `0x84`, `0x85`, `0x86`, `0x88`, `0x8C`,
`0x8D`, and `0x8E` spare page-register cells to the existing native DMA
composition. They are local byte registers, distinct from DMA channel page
registers and no-op-free. This part does not add a DMA requester, storage,
video, firmware helper, or browser behavior.

P2 implements the complete source-established spare group, not just the
observed `0x84` path. Every cell retains a byte independently, resets to zero,
remains byte-wide, and coexists with the channel page-register mapping.

The selected-ROM trace advances from two to 34 instructions and then reaches
an unmapped physical read at `0xE0000` from `F000:F94F`. The original plan
assumed a floating `0xFF` value. Controlled PCjs lockstep later established a
zero read for the selected machine, recorded by M2 T5 S6 P109; ignored writes
remain modeled without mapping synthetic RAM or ROM.

## P3 ROM Checkpoint Advance

P3 will rerun the selected-ROM trace through the native spare-register path,
record observed POST checkpoint values, and classify the next first unavailable
hardware boundary. It will not claim POST completion or add a response for an
unclassified port.

## P4 FPU Control Ports

P4 adds the complete PC/AT coprocessor-control pair: `0xF0` clear-busy and
`0xF1` reset. Both accept only byte-wide zero output, as established by PCjs.
The implementation records hardware control-line events but does not add an
x87 execution engine, firmware behavior, or an artificial completion result.
The selected trace is rerun afterwards to classify the next boundary.

## P5 DeskPro Secondary PIT

P5 adds the selected DeskPro 386 second 8254 as an opt-in configuration at
`0x48`-`0x4B`. It owns counters 3-5 and their control register, reuses the
project-native 8254 counter core, and has no generic PC/AT mapping or assumed
IRQ wiring. Its known fail-safe and refresh-related output wiring remains a
future source-classified concern. The selected trace then stops at `0x3F2`,
the floppy-controller digital-output register; no FDC behavior is added here.

## Later Checkpoint Paths

Later parts will proceed only from the latest classified trace blocker,
adding complete source-established device behavior and updated ledger evidence
per hardware path.
